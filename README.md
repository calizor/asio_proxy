
# asio_proxy

HTTPS MITM-прокси на C++17 поверх **Boost.Asio** / **Boost.Beast** и **OpenSSL** с потокобезопасным LRU-кэшем ответов, гибкой маршрутизацией доменов (MITM / blind tunnel) и live-панелью мониторинга трафика в браузере.

> ⚠️ **Только для собственных/тестовых сетей.** Проект перехватывает и расшифровывает HTTPS-трафик путём подмены сертификата на лету. Используйте его только на устройствах и в сетях, на которые у вас есть право это делать (учебный стенд, собственная лаборатория, анализ собственного трафика). Установка корневого сертификата прокси в доверенные без согласия владельца устройства — незаконна.

## Возможности

- **MITM и blind tunnel по конфигу.** `DomainConfig` читает `proxy.conf` и для каждого домена из заголовка `Host` решает: расшифровывать TLS (MITM) или молча пробрасывать байты (tunnel). Из коробки в tunnel уходят OCSP/CRL-инфраструктура, обновления ОС/браузеров, банковские сервисы с pinned-сертификатами и E2E-мессенджеры — там, где MITM ломает соединение.
- **Динамическая генерация сертификатов.** `CertManager` на лету создаёт X.509v3-сертификат (RSA-2048, SAN на домен и wildcard-поддомен), подписывает его собственным root CA и кэширует в двух уровнях: в памяти (`ssl::context`) и на диске (`certs/*.crt`, `certs/*.key`), чтобы не генерировать заново после рестарта.
- **Потокобезопасный LRU-кэш ответов** (`lru_cache.hpp`) с TTL: разбирает `Cache-Control`, `Pragma` и `Expires` по мотивам RFC 7234, отличает "не брать из кэша для этого запроса" (bypass) от инвалидации записи.
- **Многопоточность.** `io_context` с настраиваемым числом воркеров; каждое соединение получает свой `strand`, поэтому колбэки одной сессии не гоняются параллельно.
- **Live-панель мониторинга "ProxyShark"** (`panel.html`) — WebSocket-канал (`LogServer`) транслирует в браузер каждую стадию обработки запроса (CONNECT, MITM/TUNNEL, CACHE_HIT/MISS, RESPONSE, TIMEOUT, ERROR) с методом, доменом, путём, статусом, размером и задержкой — по аналогии с Wireshark.
- **Корректное завершение** по `SIGINT`/`SIGTERM`: останавливает `io_context`, дожидается воркеров, аккуратно освобождает `LogServer` до уничтожения контекста.

## Архитектура

```
main.cpp
 ├─ LogServer        — WebSocket-сервер веб-панели (порт 8081)
 ├─ DomainConfig      — парсинг proxy.conf, решение MITM/TUNNEL по домену
 ├─ LRUCache          — общий потокобезопасный кэш ответов (shared_ptr на все сессии)
 └─ ProxyServer       — accept-loop на порту 8080
     └─ ConnectionHandler       — читает CONNECT, определяет домен из Host
         ├─ MitmSession         — TLS-handshake с клиентом (сертификат из CertManager),
         │                        TLS-handshake с целевым сервером, кэширование, keep-alive
         └─ TunnelSession       — блайнд-проброс байт в обе стороны, без расшифровки
```

Структура каталогов:

```
src/
├── main.cpp
├── proxy_server.hpp        # accept-loop
├── connection_handler.hpp  # разбор CONNECT, выбор MITM/TUNNEL
├── domain_config.hpp       # правила маршрутизации доменов
├── cert_manager.hpp        # генерация и кэш X.509-сертификатов
├── lru_cache.hpp           # LRU-кэш ответов + разбор Cache-Control
├── log_server.hpp          # WebSocket-сервер для панели
└── sessions/
    ├── mitm_session.hpp    # расшифровка TLS + кэш + keep-alive
    └── tunnel_session.hpp  # blind TCP tunnel
panel.html                  # веб-панель "ProxyShark"
proxy.conf                  # правила tunnel/mitm по доменам
CMakeLists.txt
```

## Требования

- Компилятор с поддержкой C++17
- CMake ≥ 3.30
- Boost (заголовки Asio и Beast)
- OpenSSL
- nlohmann-json

Установка зависимостей:

```bash
# Debian/Ubuntu
sudo apt install libboost-all-dev libssl-dev nlohmann-json3-dev cmake build-essential

# vcpkg
vcpkg install boost-asio boost-beast openssl nlohmann-json
```

## Сборка

```bash
git clone https://github.com/calizor/asio_proxy.git
cd asio_proxy
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Бинарник появится в `build/server`.

Для отладки гонок данных доступен флаг санитайзера:

```bash
cmake -S . -B build -DSANITIZE=thread   # или -DSANITIZE=address
cmake --build build -j
```

## Настройка корневого CA

`CertManager` ожидает в рабочей директории сервера файлы `rootCA.crt` и `rootCA.key` — этим ключом подписываются все сертификаты, которые прокси выдаёт "на лету". Сгенерировать их можно так:

```bash
openssl genrsa -out rootCA.key 2048
openssl req -x509 -new -nodes -key rootCA.key -sha256 -days 3650 \
    -out rootCA.crt -subj "/C=RU/O=asio_proxy/CN=asio_proxy Root CA"
```

Чтобы браузер/ОС не ругались на подменённые сертификаты, добавьте `rootCA.crt` в доверенные корневые сертификаты **той машины, трафик которой вы анализируете и которой владеете**. Сгенерированные сертификаты для отдельных доменов CertManager сохраняет в `certs/` и переиспользует между запусками.

## Конфигурация доменов (proxy.conf)

`proxy.conf` лежит рядом с исполняемым файлом и описывает, какие домены идут в blind tunnel, а какие — в MITM:

```ini
[tunnel]
# домен и все его поддомены пойдут напрямую, без расшифровки
ocsp.digicert.com
paypal.com
whatsapp.com     # комментарии после # тоже поддерживаются

# необязательная секция: если непустая — MITM только для перечисленных
# доменов, всё остальное автоматически уходит в tunnel
[mitm]
# github.com
```

Правила:
- `[tunnel]` имеет приоритет над `[mitm]`.
- Совпадение — по домену целиком или по поддомену (`cdn.example.com` матчится записью `example.com`).
- Если файл не найден — используются встроенные дефолты (OCSP/CRL, апдейты ОС, банки, мессенджеры, Apple-сервисы).
- Если секция `[mitm]` пуста или отсутствует — по умолчанию всё, что не в `[tunnel]`, идёт в MITM.

## Запуск

```bash
cd build
./server <число_потоков>
# например:
./server 4
```

Сервер поднимает:
- `8080` — сам прокси (HTTP CONNECT); настройте его как HTTP(S)-прокси в браузере или ОС;
- `8081` — WebSocket для веб-панели.

Plain-HTTP (без `CONNECT`) прокси не поддерживает и отвечает `501 Not Implemented` — актуально только для HTTPS-трафика, который любой современный браузер туннелирует через `CONNECT`.

## Веб-панель мониторинга

Откройте `panel.html` в браузере — он подключится по WebSocket к порту `8081` и будет показывать живую ленту трафика: тип события (CONNECT/MITM/TUNNEL/CACHE_HIT/CACHE_MISS/RESPONSE/TIMEOUT/ERROR), метод, домен, путь, HTTP-статус, размер тела и задержку — как в Wireshark, но только для того, что проходит через прокси.

## Известные ограничения

- **Серийный номер сертификатов фиксирован (=1)** для всех выпускаемых сертификатов — формально нарушает RFC 5280 для CA. Большинство браузеров это терпит, но более строгие проверки могут в будущем начать отклонять такие цепочки.
- **Генерация сертификата сериализована.** `CertManager::get_context_for_domain` держит единый `std::mutex` на всё время RSA-keygen + подписи (~50 мс), поэтому первые запросы к разным новым доменам друг друга блокируют. Для прогретого кэша это не заметно.
- Поддерживается только HTTPS через `CONNECT`; plain-HTTP-проксирование не реализовано.
- Формат `proxy.conf` не валидирует домены — некорректная запись просто не совпадёт ни с чем.
